Deploying the 4 MUR Containers to MAAP (DPS)

Migration plan for running the MUR SST pipeline (landice, l2p, iquam, mrva) on NASA's MAAP platform via OGC Application Packages.
Source: mur/run_mur_pipeline.py · MAAP docs: OGC App Packages, Transition to OGC, STAC Search, Job Management · Updated July 2026

1. Context & core insight

The MUR SST pipeline currently runs as a host-side orchestrator (run_mur_pipeline.py) that shells out to docker run per stage, mounting local dirs and passing positional args. On MAAP each job is a container; there is no nested Docker. But the real shift is simpler than "rewrite everything":

The key insight: the containers themselves barely change. They already take arguments and read/write fixed paths. The work is:
(1) switch from positional to named arguments (OGC requirement, easy);
(2) make the containers dual-mode (local Docker or MAAP) via an env flag;
(3) move all the "magic" into the orchestration layer — discovery (STAC), staging (S3/CWL), caching (S3 existence check), and chaining (job outputs → next job's inputs).

This plan replaces the earlier HySDS/algorithm_config.yaml approach with the OGC Application Package model (CWL + Docker), which is MAAP's preferred path for custom "bring your own container" deployments.

2. What goes away

  • Deleted Cron-based L2P downloads — podaac-data-subscriber, .netrc credentials, the stateful .update watermark, the entire mur-l2p-dl stage. L2P granules already live in-region on S3; we reference them directly via STAC.
  • Deleted Local filesystem assumptions — Path.exists() for cached BICs, the NAS mount paths, year/DOY directory globs. Replaced by S3 lookups in the driver.
  • Deleted Positional argument convention — all containers switch to named args (--year, --doy, etc.).

3. Target architecture

maap-py driver (ADE notebook / scheduled cron)
   |
   |  STAC/CMR queries (pystac-client) resolve:
   |    - L2P granule S3 hrefs per sensor/day (no download needed)
   |    - Existing BIC/iquam/landice/CSP outputs in S3 (skip-if-exists)
   |
   |  For each analysis day in the processing window (sequential):
   |
   |- OGC execute: mur-landice  --year Y --doy D                          → S3: landice/{p011,p01}
   |- OGC execute: mur-iquam    --year Y --doy D                          → S3: iquam/.bii
   |- OGC execute: mur-l2p      --sensor S --year Y --doy D --rewrite 0   → S3: bic/{sensor}/{year}/{doy}.bic.gz
   |      (input: L2P .nc hrefs from STAC — DPS stages into input/)
   |
   '- OGC execute: mur-mrva     --year Y --doy D --mode nrt               → S3: netcdf/ + csp/
          (inputs: BIC + iquam + landice + prior-day CSP — all staged into input/)
          (output CSP feeds into next day's MRVA job)
   |
   [next day: repeat, chaining prior CSP → ...]

The driver handles all STAC queries, caching checks, NRT/REA logic, and stage ordering. Containers remain science-focused: read input/, write output/, accept named arguments.

4. Container changes — the dual-mode approach

4.1  Named arguments (OGC requirement)

The OGC Application Package model requires named arguments: run.sh --year 2026 --doy 15 --mode nrt instead of run.sh 2026 15 nrt. This is the one universal change to all four containers.

Implementation: a thin wrapper in each entrypoint.sh that detects whether args are named (--year present) or positional (first arg is a bare number). This lets the same image work both locally (docker run mur-landice 2026 15) and on MAAP (--year 2026 --doy 15).

# Dual-mode argument parsing (sketch for all 4 containers)
if [[ "$1" == --* ]]; then
    # Named mode (MAAP / OGC)
    while [[ $# -gt 0 ]]; do
        case "$1" in
            --year)   YEAR="$2";   shift 2 ;;
            --doy)    DOY="$2";    shift 2 ;;
            --mode)   MODE="$2";   shift 2 ;;
            --sensor) SENSOR="$2"; shift 2 ;;
            # ... per container
            *) shift ;;
        esac
    done
else
    # Positional mode (local docker run, backwards compatible)
    YEAR="$1"; DOY="$2"; MODE="$3"  # etc.
fi

4.2  Input/output path abstraction

Each container already reads from fixed internal paths (/input, /data/input, /data/output). For MAAP, the entrypoint checks an env var (MAAP_MODE=1 or simply detects ./input/ exists) and remaps:

ModeInputOutput
Local DockerBind-mounted host dir at /input or /data/inputBind-mounted host dir at /output or /data/output
MAAP / OGC$PWD/input/ (DPS-staged files)$PWD/output/ (auto-uploaded to S3)

This is a symlink or variable assignment at the top of entrypoint.sh — no MATLAB code changes.

4.3  Static resources (coefficients, grids, masks)

MRVA needs ~5 GB of static resources (analysis grids, land masks, prior-day coefficients) that don't change run-to-run. Staging them fresh every job is wasteful. Two options:

  • Bake into the image (recommended if <2 GB after compression). These are already in testing/static-resources and rarely change. Simplest, no per-job I/O cost.
  • S3 Mountpoint FUSE if they're large or independently versioned — the container mounts an S3 prefix as a local path. Verify DPS workers permit FUSE. Alternatively, the driver passes them as CWL Directory inputs staged once per job.

Either way MRVA reads local paths — it never calls S3 APIs directly.

6. Output registration (STAC)

6.1  Which outputs need registration?

L2P BIC filesNoIntermediate cache; consumed by MRVA. Deterministic S3 prefix is sufficient for lookup.

6.2  STAC publish flow for MRVA output

After a successful MRVA job the driver (not the container) registers the output:

  1. Reads the MRVA job's S3 output path via getJobResult().
  2. Constructs a STAC Item with metadata extracted from the NetCDF (or from the job params):
    • datetime: analysis date
    • bbox: [−180, −90, 180, 90] (global)
    • geometry: global polygon
    • collection: a pre-defined MUR L4 SST collection in MAAP STAC
    • assets.data.href: the S3 path
    • Properties: version, mode (nrt/rea), processing date, etc.
  3. Publishes the STAC Item to MAAP STAC (the user-produced-data catalog at stac.maap-project.org). This may require coordination with the MAAP data team to create the collection initially, after which per-granule item ingest can be automated.
Confirm with MAAP ops: whether self-service STAC item ingest is available via API, or whether collection creation + initial ingest requires the data team. Per-granule ingest after collection setup should be automatable via maap-py or direct STAC Transaction API.

7. Data flow: STAC replaces downloads

7.1  L2P granule discovery (the big win)

Today: cron runs podaac-data-subscriber hourly with Earthdata creds and a .update watermark, downloading .nc files to disk. The L2P container then globs that disk directory.

On MAAP: the granules are already in S3 (PODAAC distributes through NASA's cloud archive). No download. No credentials. No watermark state. The driver does a STAC query:

from pystac_client import Client

cat = Client.open("https://stac.maap-project.org/")  # or CMR STAC
items = cat.search(
    collections=["AMSR2-REMSS-L2P-v8.2"],
    datetime="2026-07-01/2026-07-02",
    bbox=[-180, -90, 180, 90]
).items()

# These are already in-region S3 — pass directly as CWL File inputs
granule_hrefs = [item.assets["data"].href for item in items]
# e.g. s3://podaac-ops-cumulus-protected/AMSR2-REMSS-L2P-v8.2/...

The driver passes these hrefs to the L2P job as CWL File inputs. DPS stages them into input/. The container reads local files exactly as today. Zero container code change for discovery.

The BIC reuse pattern (one BIC per sensor-per-day consumed by ~5 overlapping analysis dates) is preserved unchanged. Only the storage medium and existence-check move:

8. OGC Application Package registration

8.1  Why OGC (not classic HySDS algorithm_config.yaml)

  • MAAP's OGC path is purpose-built for "bring your own container" — you point at an arbitrary image in a registry; no need for maap_base or conda.
  • Inputs/outputs are declared in CWL (typed: File, Directory, string, int) with explicit stage-in/stage-out semantics.
  • The container is invoked via CWL's DockerRequirement.dockerPull with a baseCommand + arguments. Named args are mandatory.

8.2  Per-algorithm CWL sketch

Each container gets a CWL CommandLineTool + wrapping Workflow. Example for mur-l2p:

class: CommandLineTool
baseCommand: ["/opt/l2p/bin/entrypoint.sh"]
requirements:
  DockerRequirement:
    dockerPull: mas.maap-project.org/<org>/mur-l2p:latest

inputs:
  sensor:
    type: string
    inputBinding: { prefix: "--sensor" }
  year:
    type: int
    inputBinding: { prefix: "--year" }
  doy:
    type: int
    inputBinding: { prefix: "--doy" }
  rewrite:
    type: int
    inputBinding: { prefix: "--rewrite" }
  granules:
    type: File[]
    inputBinding: { prefix: "--input-dir" }  # or staged to input/

outputs:
  bic_file:
    type: File
    outputBinding: { glob: "output/*.bic.gz" }
Confirm: exact CWL schema against the MAAP OGC registration tutorial and transition guide during implementation. The sketch above shows the pattern; field names and input-binding semantics may differ.

8.3  Image registry

  • Build locally (where the MATLAB license server is reachable), tag, push to mas.maap-project.org/<org>/mur-{landice,l2p,iquam,mrva}:<version>.
  • network.lic is compile-time only; no license in the deployed image.
  • The OpenShift arbitrary-UID pattern already in the Dockerfiles (chgrp -R 0, HOME=/tmp, MCR_CACHE_ROOT=/tmp) is exactly what DPS workers expect.

9. The orchestration driver (where the "magic" lives)

New mur/run_mur_maap.py alongside the existing run_mur_pipeline.py (which continues to work for local Docker). Same decision logic, different executor.

What the driver does (all cloud-native concerns live here):

  1. Date/mode calculation — unchanged: mur_date, calculate_processing_window, is_nrt_mode, stablat, dayrange.
  2. STAC discovery — queries CMR/MAAP STAC for L2P granule S3 hrefs per sensor/day.
  3. Cache check — S3 HEAD on the deterministic BIC/iquam/landice prefixes; skips jobs whose outputs already exist (same semantics as Path.exists() today).
  4. Job submission — OGC API Processes execute per container, passing named args + File/Directory inputs.
  5. Polling + chaining — waits for upstream stages, collects S3 output hrefs, feeds them to downstream stages (L2P outputs → MRVA inputs).
  6. STAC publish — after MRVA success, constructs and publishes STAC Item for the MUR L4 SST granule.
# Pseudo-flow in the driver
for process_date in date_window:
    is_nrt = is_nrt_mode(process_date, day1)

    # Preprocessing (parallel where possible)
    landice_job = submit("mur-landice", year=Y, doy=D)
    iquam_job   = submit("mur-iquam",   year=Y, doy=D)

    # L2P per sensor (STAC query + BIC cache check)
    for sensor in active_sensors:
        for data_day in dayrange_window(process_date):
            if bic_exists_in_s3(sensor, data_day) and not needs_rewrite(data_day):
                continue
            granules = stac_search(sensor, data_day)  # S3 hrefs, no download
            submit("mur-l2p", sensor=sensor, year=Y, doy=D, rewrite=R, inputs=granules)

    # Wait for all preprocessing
    wait_all([landice_job, iquam_job, *l2p_jobs])

    # MRVA (fan-in all preprocessed outputs)
    bic_hrefs     = list_s3("mur/bic/", sensor_days)
    iquam_hrefs   = list_s3("mur/iquam/", ...)
    landice_hrefs = list_s3("mur/landice/", ...)
    mrva_job = submit("mur-mrva", year=Y, doy=D, mode=mode,
                      inputs=[bic_hrefs, iquam_hrefs, landice_hrefs])

    # STAC publish
    wait(mrva_job)
    publish_stac_item(mrva_job.output_href, process_date, mode)

10. MRVA decomposition: one job per analysis day

10.1  Why break up the multi-day loop

Today run_mur_pipeline.py loops over the processing window (up to 9 days) and calls MRVA once per day sequentially. On MAAP the same pattern applies — but as one DPS job per analysis day rather than one giant multi-day job.

Benefits of per-day MRVA jobs:
  • Smaller blast radius — a failure on day 5 doesn't lose days 1–4
  • Better resource accounting — each job runs 30–90 min, well within queue timeouts
  • Restartable — retry a single failed day without re-running the entire window
  • Observable — per-day job status, logs, memory usage tracked independently
  • Fits cloud billing — precise per-day cost attribution

10.2  The day-to-day dependency: prior CSP coefficients

MRVA is not embarrassingly parallel across days. Each analysis day uses the prior day's CSP (coefficient) output as its starting first-guess. This is why production processes days in order. The dependency chain:

Day N-1 MRVA  ──CSP output──>  Day N MRVA (--prior-csp <S3 href>)  ──CSP output──>  Day N+1 MRVA ...

The driver submits MRVA jobs sequentially, passing the prior day's CSP S3 href as a CWL File input to the next:

# Driver pseudo-code for the MRVA date loop
prior_csp_href = get_latest_csp_from_s3(day_before_window)  # cold-start / last operational run

for process_date in date_window:   # e.g. T-9 through T-1
    mode = "rea" if process_date <= day1 else "nrt"
    mrva_job = submit("mur-mrva",
                      year=Y, doy=D, mode=mode,
                      prior_csp=prior_csp_href,
                      bic_inputs=bic_hrefs[process_date],
                      iquam_input=iquam_hrefs[process_date],
                      landice_input=landice_hrefs[process_date])
    wait(mrva_job)
    prior_csp_href = mrva_job.output("csp")   # chain to next day
    publish_stac_item(mrva_job.output("netcdf"), process_date, mode)

10.3  Cold start: where does the first day's prior-CSP come from?

Three cases:

  • Normal operations: yesterday's MRVA run already produced a CSP file sitting in S3 at the deterministic prefix. The driver retrieves it.
  • First-ever run / gap recovery: MRVA uses a static climatological first-guess (already part of the static resources baked into the image or staged from S3). No external dependency.
  • Reprocessing (--date): the driver looks up the CSP from the day immediately before the reprocessing window in S3.

10.4  Container change for per-day mode

The MRVA container already processes a single (year, doy, mode) tuple per invocation — no change to its core interface. The only new input is --prior-csp <path>, which the entrypoint maps to the appropriate internal location (where mrva4com.m expects the prior-day CSP file). If omitted, MRVA falls back to the static first-guess (existing behavior for the first day of a window).

13. Verification plan

  1. Single stage smoke test. Register mur-iquam (self-contained, downloads from NOAA). Submit on a small queue. Confirm .bii appears in S3 output/.
  2. STAC-driven L2P. Driver queries STAC for one sensor-day, passes hrefs to mur-l2p job. Confirm BIC lands at the deterministic S3 prefix. Run a second time: confirm the driver's cache check skips re-submission.
  3. MRVA on the large queue. Submit one NRT analysis day with chained BIC + iquam + landice S3 inputs. Confirm MUR NetCDF is produced.
  4. Scientific equivalence. Compare MAAP-produced NetCDF against a local docker run reference for the same date (reuse mur/eval.py / mur/compare_bic.py). Must be byte-comparable within floating-point tolerance.
  5. Full-day driver test. Run run_mur_maap.py --date <D> -p -1 (NRT) and a REA boundary day. Confirm stage ordering, NRT/REA mode, stablat skip/rewrite, and STAC publish all behave correctly.
