Static input data

The reference files the pipeline needs on disk before it can run, and where they come from.

What counts as static

Alongside the observations it downloads each day, the pipeline needs a set of reference files that change rarely or never: land masks, grid transformation matrices, and a day-of-year climatology. These are not fetched automatically — they must be staged before the first run.

Layout

static-resources/
├── grids/                    # land/sea masks
│   ├── maskGLOBp01deg.gds    # 0.01° (36000 x 17999)
│   ├── maskGlob1km.gds       # 0.011° (~1 km)
│   └── MUR25grid.gds         # 0.25°, for the MUR25 product
├── mat/                      # OSI-SAF -> analysis grid mappings
│   ├── p01/{saf2north,saf2south}.mat
│   └── p011/{saf2north,saf2south}.mat
├── seasonal/                 # day-of-year climatology
│   └── mur_001.nc ... mur_365.nc
├── landice/
│   └── CylinderP01_edge.bip  # polar cap edge
└── L4/                       # optional bootstrap reference
    └── GLOB/NCDC/AVHRR_OI/<year>/<doy>/

The four saf2*.mat matrices are the bulk of it — roughly 500 MB between them. They are derived data, reproducible from the land masks plus some small OSI-SAF index files, so they need not be archived if the generators are available.

L4/ is optional. It provides a background field only in the bootstrap case where no prior coefficient exists at all; in normal operation the analysis builds its own reference and never reads it. A host without the L4 archive runs fine.

How these reach the containers

Each file is passed as its own named flag — --landmask-p01-file, --seasonal-file, --polar-cap-edge-file and so on — resolved by the orchestrator and bind-mounted individually. No container is handed the static-resources/ root and left to find its own way around, which is why moving or renaming a file surfaces immediately as a named error rather than a mysterious read failure.

Sea ice concentration

Sea ice is the one input fetched at run time rather than staged. It comes from OSI-SAF over HTTPS, selected by three environment variables:

VariableCoversDefault
OSISAF_FTP_PRODCurrent dayOSI-SAF THREDDS amsr2_conc tree
OSISAF_FTP_ARCHIVERecent daysSame tree
OSISAF_FTP_REPROCESSEDPre-2009 datesNone — must be supplied explicitly

The variables keep their _FTP_ names for interface compatibility, but OSI-SAF's anonymous FTP host no longer answers — connections to it hang until they time out. The defaults are HTTPS endpoints; an ftp:// value still works if you supply one, since the reader dispatches on the URL scheme.

AMSR2 and AMSR3

OSI-SAF replaced the AMSR2 instrument with AMSR3 inside the same amsr2_conc tree: files are named ice_conc_<hem>_polstere-100_amsr2_… through 2026-08-30 and …_amsr3_… from 2026-08-31, with no overlap. The products are otherwise identical — same grid, same variables, same scaling — so only the filename changes.

The reader selects the token by date, because reprocessing an older day still needs the AMSR2 name. The cutover can be moved with OSISAF_AMSR3_START=YYYYMMDD if the upstream naming shifts again, which avoids a rebuild.

File-by-file detail, sizes, formats and provenance are in STATIC_DATA.md; the mask bit layout is in LANDICE_ENCODING.md.
