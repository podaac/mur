Running on MAAP

How the four containers execute as OGC Application Packages on NASA's MAAP platform, and which parts of that are the platform's job rather than ours.

For the step-by-step procedure — getting a token, staging the static data, registering the algorithms, launching a day — see Deploying to MAAP. This page is the reference for how it works.

The execution model

MAAP runs an algorithm as an OGC Application Package: a CWL workflow plus a container image. The same four images that run_mur_pipeline.py drives with docker run locally are executed by MAAP's DPS instead, with run_mur_maap.py's MAAPOrchestrator standing in for the local MUROrchestrator.

The two orchestrators share their decision logic on purpose. The processing window, NRT/REA mode, rewrite decisions and day-range iteration all live in mur_window.py, imported by both, and tests/test_mur_window.py compares the two classes across sixty consecutive dates so they cannot drift. What differs is only the executor: one shells out to Docker, the other submits jobs.

Earlier versions of this page described submission as WPS 2.0 Execute XML and said the OGC branch was not public. Both are now obsolete. maap-py 5 and later expose OGC API Processes: deploy_algorithm, deploy_algorithm_from_cwl_file, submit_job, get_job_status, get_job_result and list_jobs.

Pre-built images are supported directly. An algorithm_config.yml that sets algorithm_container_url needs no Dockerfile at registration time, so the images built by utils/build_and_push.sh are referenced as they are. The four configs live under maap/.

Deploying registers; it does not provision

Deploying an application package creates a catalogue entry and nothing else. No hardware is allocated, no image is pulled, no capacity is reserved. The queue is chosen at submit_job rather than at deploy time, and ResourceRequirement's ramMin/coresMin are a declaration the scheduler reads when a job arrives — not a reservation held on the package's behalf.

A registered process carries a numeric processID, which is what execution takes; the id field is the algorithm name. Registering the same algorithm at a new version mints a new processID, so it is looked up rather than pinned.

A successful deployment says nothing about whether the algorithm runs. dockerPull is a reference resolved at job runtime, so a private package, a wrong tag or an unreachable registry all register cleanly and fail on first execution. That is why the first job is a deliberate smoke test rather than the start of a backfill — it is the first moment anything actually tries to pull the image.

Why a second image per module

Each module image sets ENTRYPOINT ["/opt/<module>/bin/entrypoint.sh"], which is right for docker run <image> --year 2026 …. But Docker appends a command to an ENTRYPOINT rather than replacing it, and CWL supplies its own baseCommand — so a CWL job would execute

entrypoint.sh /opt/landice/bin/entrypoint.sh --year 2026 ...

and every MUR entrypoint rejects unknown positional arguments. MAAP's own reference application declares no ENTRYPOINT for the same reason. maap/Dockerfile.dps derives a -dps image that clears it. The change is metadata only: no layer content, no MATLAB Runtime rebuild, and local execution keeps using the base image untouched.

What a container receives

Every input is a named flag carrying a single scalar — there are no array inputs, and no File or Directory types. Flag values are s3:// hrefs, which common/bin/localize.sh fetches with aws s3 cp before MATLAB starts. The container's own scanning and lookup logic is unchanged from local execution, because it operates on a materialized directory either way.

Only MRVA needs a large instance, and the cost is almost entirely the finest level. The analysis runs to LF=11, where infoMatrix is 49.3 GiB in NRT and 53.7 GiB in REA, for a working set near 55 GiB. Production peaks around 72 GB once MATLAB is counted — it stays resident while the Fortran runs — so 64 GiB is the largest pool available rather than a comfortable one.

DPS has no swap, and swap would not rescue this anyway: the PCG solver streams the entire matrix once per iteration, so paging it would cost about 18 seconds per iteration on NVMe before any arithmetic, against thousands of iterations. Note also that cwltool runs containers without --memory, so there is no cgroup limit and an exit 137 is the host kernel's OOM killer.

An earlier version of this page said the analysis reached L=9 at roughly 60 GB. That came from a memory analysis whose table is shifted two levels, overstating every level by 17.4×; its “L=9, 53.71 GB” is really L=11. The real L=9 needs 3.46 GiB. See the correction at the top of mrva/docs/MEMORY_ANALYSIS_AND_MATRIX_FREE_PLAN.md.

Two flags are deliberately not exposed. --l4-reference-root names a directory tree, and localize.sh's aws s3 cp has no --recursive, so an s3:// value passes through unfetched and verify_inputs_exist rejects it — passing it breaks the job rather than enabling the bootstrap fallback it was meant to provide. iQUAM's --work-dir, --log-dir and --output-dir are placement detail the caller cannot know on DPS, so they keep in-container defaults.

Fan-in: the manifest mechanism

L2P's granules and MRVA's BIC + iQUAM inputs are variable-count, which a scalar flag cannot express. Each is instead a single --<name>-manifest flag pointing at a JSON file; see Input contract for the schema. localize_manifest fetches the manifest, then materializes every listed entry into a scratch directory using its relative_path.

A CWL Directory input, which MAAP would stage in automatically, was considered and rejected for three reasons:

  • There is no single prefix to stage. L2P's granules are arbitrary hrefs across PO.DAAC collections; MRVA's fan-in spans roughly thirty unrelated DPS output prefixes.
  • It would over-fetch catastrophically. A Directory on seasonal/ would transfer the whole ~141 GB archive to read the one 396 MB file that day needs.
  • It cannot carry identity. The manifest's sensor and relative_path fields reproduce the <SENSOR>/<YEAR>/<file> layout mrva4com_container.m's per-sensor scan expects. A staged directory arrives in whatever shape the producer happened to use.

Stage-out, and who chooses the path

CWL collects glob: ./output* relative to the job's working directory. Anything written to an absolute path outside it is simply not collected — a job would run to completion and stage out an empty directory.

All four containers therefore derive their output root from MUR_OUTPUT_ROOT, defaulting to $PWD/output. run_mur_pipeline.py passes MUR_OUTPUT_ROOT=/data/output so local behaviour is unchanged. MRVA is the exception: its paths are compiled into mrva4com_container.m, so until the next MATLAB rebuild the entrypoint symlinks /data/output/{csp,netcdf} at the real output directory, with a copy fallback if the symlink is refused. It logs which branch fired.

Who controls a path. Anything we write — static resources, manifests, promoted artifacts, STAC items — goes to a key we choose. Anything DPS writes lands under dps_output/<algorithm>/<tag>/<date>/<time>/, where the job tag is the only caller-controlled component. That split is what the promotion step below exists to bridge.

Where generated files are catalogued

Three layers, with different owners.

1. Jobs — MAAP maintains this

maap.list_jobs() is a queryable record of every job ever submitted, filterable by process, status, queue, tag and datetime range. Nothing to maintain. This is why job tags are deterministic and self-describing (mur.<run_id>.<role>.<key>) — it makes that catalogue queryable by meaning rather than by opaque id. But it is job-shaped, not product-shaped: finding a particular BIC means first finding the job that produced it.

2. Intermediates — deterministic keys, not STAC

BIC files, iQUAM .bii, landice per-day outputs and the .c06 coefficient are promoted after their job succeeds: copied from the DPS-chosen path to a canonical key under the workspace bucket (mur_maap/paths.py). That converts a path we do not control into one we do, at the one moment we still hold the job id.

Without it, the BIC cache is decorative — an artifact left where DPS put it is invisible to tomorrow's run, whose only route back to it is a job id a later invocation does not have. Promotion is what makes --prior-csp-file work too: this day's coefficient lands at a known key, and the next day's run chains from it instead of bootstrapping.

These are deliberately not registered in STAC. They churn daily, they are internal plumbing, and cataloguing them would mean thousands of items nobody queries. A single S3 HEAD is cheaper and simpler than a catalogue round-trip.

3. The L4 granule — STAC

The product is where discovery is the point. mur_maap/stac.py builds the Item as a pure function, so the metadata shape is testable without an endpoint or credentials. The Item id carries the mode (mur-l4-20260806-nrt), because a day is first produced as NRT and later reprocessed as REA — collapsing both onto one id would let the reanalysis silently replace the interim.

The static resources are not catalogued either, for the same reason as the intermediates: containers receive explicit hrefs built by joining a configured root with a fixed relative path, so nothing ever searches for them.

Surviving an idle-culled workspace

One analysis day is 28 jobs — landice, iQUAM, 25 L2P jobs across five sensors and their day windows, then MRVA. That is far longer than any idle timeout, and the JupyterHub server is culled when idle. The home directory and the S3 buckets persist; a running process does not.

So the orchestrator persists submitted job ids and per-stage status, and is re-enterable rather than blocking. Two fields carry the design:

  • reference_today is frozen at run creation. Recomputing it on resume would shift the NRT/REA boundary and every rewrite decision mid-flight, days after the jobs were planned.
  • config_fingerprint refuses a resume against an edited config, which would silently change what already- submitted jobs mean.

If the state file itself is lost, every job tag is recomputable from the plan alone, so list_jobs(tag=…) rebuilds it from live MAAP truth.

Still unverified

Each of these is an assumption that has not met a real endpoint. They are listed rather than resolved because guessing would be worse than waiting.

  • get_job_result()'s return shape — a directory prefix, per-file hrefs, or a dict keyed by CWL output id. It gates output matching, so one real landice job should be run and its response recorded before any code is written against it.
  • A queue offering 64 GiB and 16 cores for MRVA. Nothing else needs one. Worth confirming before registering anything, since it is the cheapest question to ask and the most expensive to discover late.
  • DPS ephemeral disk. L2P materializes every granule to scratch — a MODIS day is roughly 288 granules at ~20 MB, and a worst case exceeds 20 GB. outdir_max does not reserve scratch.
  • Outbound egress from DPS workers. landice fetches OSI-SAF sea ice; iQUAM fetches NOAA STAR. (A worker does reach ghcr.io and S3, so egress is not blocked wholesale.)
  • The runtime UID/GID, which decides whether MRVA's symlink stage-out works or falls back to copying.
  • submit_job(inputs=)'s shape — plain {"name": value} or OGC {"name": {"value": …}}, and whether non-string scalars are accepted.
  • list_jobs(tag=) — exact or prefix matching, and whether dedup keys on inputs or tag. Promotion to canonical keys was chosen partly so cross-run lookup does not depend on the answer.

L2P granules are copied into the workspace bucket before a job reads them. A real job confirmed why: handed PO.DAAC's own href, the container fails with An error occurred (403) when calling the HeadObject operation: Forbidden on podaac-ops-cumulus-protected. A worker reads S3 as its own role, and that role has no DAAC access.

The same job proved the other half — it downloaded its manifest from the workspace bucket seconds earlier, so a worker reads that perfectly well. Copying costs duplicate storage and is the price of the 403. The cleaner fix is teaching localize.sh to mint Earthdata credentials, but it touches the file all four containers share and means rebuilding every image; a maap.granule_staging switch keeps the direct path available for when that changes.
