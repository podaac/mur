Running on MAAP

How the four containers execute as OGC Application Packages on NASA's MAAP platform, and which parts of that are the platform's job rather than ours.

For the step-by-step procedure — getting a token, staging the static data, registering the algorithms, launching a day — see Deploying to MAAP. This page is the reference for how it works.

The execution model

MAAP runs an algorithm as an OGC Application Package: a CWL workflow plus a container image. The same four images that run_mur_pipeline.py drives with docker run locally are executed by MAAP's DPS instead, with run_mur_maap.py's MAAPOrchestrator standing in for the local MUROrchestrator.

The two orchestrators share their decision logic on purpose. The processing window, NRT/REA mode, rewrite decisions and day-range iteration all live in mur_window.py, imported by both, and tests/test_mur_window.py compares the two classes across sixty consecutive dates so they cannot drift. What differs is only the executor: one shells out to Docker, the other submits jobs.

Earlier versions of this page described submission as WPS 2.0 Execute XML and said the OGC branch was not public. Both are now obsolete. maap-py 5 and later expose OGC API Processes: deploy_algorithm, deploy_algorithm_from_cwl_file, submit_job, get_job_status, get_job_result and list_jobs.

Pre-built images are supported directly. An algorithm_config.yml that sets algorithm_container_url needs no Dockerfile at registration time, so the images built by utils/build_and_push.sh are referenced as they are. The four configs live under maap/.

Deploying registers; it does not provision

Deploying an application package creates a catalogue entry and nothing else. No hardware is allocated, no image is pulled, no capacity is reserved. The queue is chosen at submit_job rather than at deploy time, and ResourceRequirement's ramMin/coresMin are a declaration the scheduler reads when a job arrives — not a reservation held on the package's behalf.

A registered process carries a numeric processID, which is what execution takes; the id field is the algorithm name. Registering the same algorithm at a new version mints a new processID, so it is looked up rather than pinned.

A successful deployment says nothing about whether the algorithm runs. dockerPull is a reference resolved at job runtime, so a private package, a wrong tag or an unreachable registry all register cleanly and fail on first execution. That is why the first job is a deliberate smoke test rather than the start of a backfill — it is the first moment anything actually tries to pull the image.

Why a second image per module

Each module image sets ENTRYPOINT ["/opt/<module>/bin/entrypoint.sh"], which is right for docker run <image> --year 2026 …. But Docker appends a command to an ENTRYPOINT rather than replacing it, and CWL supplies its own baseCommand — so a CWL job would execute

entrypoint.sh /opt/landice/bin/entrypoint.sh --year 2026 ...

and every MUR entrypoint rejects unknown positional arguments. MAAP's own reference application declares no ENTRYPOINT for the same reason. maap/Dockerfile.dps derives a -dps image that clears it. The change is metadata only: no layer content, no MATLAB Runtime rebuild, and local execution keeps using the base image untouched.

How a run executes

The window and mode rules are the ones in Daily execution. What changes on MAAP is the scheduling. Every stage becomes a DPS job, and run_mur_maap.py decides which jobs run together and which must wait. The pattern is a loop over days, oldest first. Within a day, the input jobs fan out, the run waits for all of them, and then MRVA runs.

  1. Loop over days, oldest first. main() calls run_day() once per day and blocks until it returns. Every REA day in the range finishes before the first NRT day starts. A failed day is logged and the loop moves on, and the exit status still reports the failure.
  2. Fan out the inputs. mur-landice, mur-iquam and every mur-l2p job are submitted before anything is waited on, because none of them depends on another. L2P submits one job per active sensor per data day in that sensor's l2p.sensors[X].day_range, dropping future days. Inputs already in the bucket are not resubmitted: landice, iQUAM, and BICs past their stable age. A typical NRT day is twenty-odd jobs.
  3. Wait for all of them. wait_all blocks until every input job has finished. Outputs from the jobs that succeeded are promoted to canonical S3 keys before the day is failed for any that did not, so a re-run submits only what is still missing. See Stage-out.
  4. Run MRVA. It reads every input through one sensor manifest (BICs plus IQUAM0) and takes about an hour. Its L4 granule is promoted and its sidecar STAC item written.
  5. Submit the browse rasters and move on. One mur-cog job each for the 1 km and MUR25 granules, submitted and never waited on. Each stages out its own catalog.json, MAAP ingests it, and every tool reads the browse layers from there (utils/mur_stac.py, utils/mur_layers.py), so the run has nothing to collect. The job ids are logged; a failure costs pictures, never the day, and shows in utils/job_logs.py.

Possible speed-up. The next day's input jobs depend on nothing from this day, so they could be submitted while this day's MRVA runs. That would hide most of the input stage. Only MRVA has to stay in day order, and it only matters on the day that receives a coefficient. Today only the browse rasters overlap the next day; the input jobs still wait for the previous day's MRVA.

The daily run is production's T-9…T-1 sweep. With no -p, which is how cron_mur_maap.sh calls it, run_mur_maap.py runs nrtMRVA.py's window. T-9…T-4 are Final (REA) days, and one whose Final granule already exists is kept, as nrtMRVA.py's KEEPING OLD does (--rerun-final redoes it). T-3…T-1 are redone as Interim (NRT) days every run. A BIC or buoy file that several days' windows reach is built once per run. Set MUR_PROCESS_DAYS=-1 in the crontab to go back to one NRT day.

Until 2026-10-28 the cron passed -p -1. As a result no day ever got a Final run, and no NRT day had a .c06 to chain from.

What counts as cached

  • BICs are rebuilt while their day is younger than the sensor's stable. After that, a BIC written fewer than stable days after its day is rebuilt once more. Without that rule a BIC was last built at 06Z the day after its data, which is before PO.DAAC had ingested everything. MODISA 2026/293 was frozen with 113 of production's 322 granules. --trust-cached-bics restores the old rule.
  • Buoy files are rebuilt while their day is younger than iquam.stable_latency (buoystablat), and a header-only file (24 bytes, no observations) is never reused or promoted. Before this, every .bii from 2026/282 on was empty and was never rebuilt.
  • Granules belong to the day they start on, as in production's -dydoy download layout. CMR's overlap search also returns the previous day's last swath, which is now dropped.

Coefficient chaining

An NRT day passes --prior-csp-file pointing at the previous day's L=6 coefficient, csp/<year>/<YYYYMMDD>09_MRVA4_Global.c06. This matches mrva4com.m's realtime branch. Only an REA run writes a .c06. REA starts at L0=2 and saves c02–c11, while NRT starts at L0=Lref=7 and saves c07–c10. The first NRT job on MAAP (2026-10-06) confirmed this: it staged out c07–c10 and no c06. So:

  • In a full -9:-1 sweep, T-3 chains from T-4's REA coefficient (the green arrow). T-2 and T-1 find no .c06 and build their reference field from scratch.
  • With the default -p -1, T-1 looks for T-2's .c06, which will not exist until T-2 is reanalysed three days later. The daily NRT run therefore always builds its reference field from scratch.

Either way the run is valid, because mrva4com_container.m treats a missing prior coefficient as a reason to bootstrap, not as an error. The orchestrator HEADs the key before passing it, so it never sends a path it has not checked.

Details

  • Two windows. l2p.sensors[X].day_range controls which BICs this run builds. mrva.sensors[X].day_range controls which ones the analysis reads. When MRVA's window reaches a day this run did not build, the orchestrator uses the BIC already in the bucket.
  • Narrowing with --execute. Leaving mrva out stops each day after the wait. With cog still included, browse rasters are generated from an L4 granule that was already promoted.

What a container receives

Every input is a named flag carrying a single scalar — there are no array inputs, and no File or Directory types. Flag values are s3:// hrefs, which common/bin/localize.sh fetches with aws s3 cp before MATLAB starts. The container's own scanning and lookup logic is unchanged from local execution, because it operates on a materialized directory either way.

ModuleStatic inputsFan-inRAM / cores
mur-landice6 explicit files—6 GiB / 2
mur-iquamnone (downloads its own)—4 GiB / 1
mur-l2pnone--granules-manifest8 GiB / 2
mur-mrva2 required + 1 optional, plus 3 landice outputs--sensor-inputs-manifest64 GiB / 16

Only MRVA needs a large instance, and the cost is almost entirely the finest level. The analysis runs to LF=11, where infoMatrix — 49 reals per spline coefficient — dominates everything else.

In real*8 that is a 55.48 GiB working set, and production peaks near 72 GB once MATLAB is counted, since it stays resident while the Fortran runs. That does not fit any pool available to us, so since 2.0.6 infoMatrix is built real*4, giving 30.77 GiB. Use maap-dps-worker-64gb even so: 30.77 GiB in a 32 GiB pool leaves about 1.2 GiB for MATLAB and the OS, which is not headroom.

The precision change is not yet validated against a reference run. The obvious check — the same day both ways — cannot be performed, because the real*8 side has nowhere to run. Validation is against production output for the same day; until that comparison exists, treat the L4 granule as provisional. Build with --build-arg INFOMATRIX_R8=1 to restore the old precision on a machine large enough for it.

DPS has no swap, and swap would not rescue this anyway: the PCG solver streams the entire matrix once per iteration, so paging it would cost about 18 seconds per iteration on NVMe before any arithmetic, against thousands of iterations. Note also that cwltool runs containers without --memory, so there is no cgroup limit and an exit 137 is the host kernel's OOM killer.

Capping the analysis when no large pool is available

Since 2.0.9 the finest scale can be capped with mrva.max_level in config.maap.json. It is deliberately absent from the example config: omitting it means the full L=2..11, which is what production delivers and what you want unless you have a specific reason otherwise.

"mrva": {
  "max_level": 10
}

The reason it exists is that L=11 needs about 28.8 GiB and no DPS pool currently provides it — both 64 GB queues fail before the container starts — while L=10 needs 13.84 GiB and completes on maap-dps-worker-32gb. Capping buys a complete, valid granule on hardware that works.

What it costs is resolution, not validity. spgrid interpolates whichever level onto the grid from the land mask, so the NetCDF has the same dimensions, the same variables, the same coordinates and the same CF attributes as a full run. Anything that opens a production granule opens this one. The field is simply smoother and lacks the operational product's finest scale, so it is not suitable for assessing fine-scale features or comparing gradients against production.

Because the two are otherwise indistinguishable, every granule records the level it was solved to in the mrva_analysis_level global attribute, and a capped one also carries mrva_analysis_level_comment. Check that before comparing any granule against production:

ncdump -h <granule>.nc | grep mrva_analysis_level

Setting it also raises a warning in the run log, since a cap is a scientific decision and a config field nobody re-reads is not a record of one.

An earlier version of this page said the analysis reached L=9 at roughly 60 GB. That came from a memory analysis whose table is shifted two levels, overstating every level by 17.4×; its “L=9, 53.71 GB” is really L=11. The real L=9 needs 3.46 GiB. See the correction at the top of mrva/docs/MEMORY_ANALYSIS_AND_MATRIX_FREE_PLAN.md.

Two flags are deliberately not exposed. --l4-reference-root names a directory tree, and localize.sh's aws s3 cp has no --recursive, so an s3:// value passes through unfetched and verify_inputs_exist rejects it — passing it breaks the job rather than enabling the bootstrap fallback it was meant to provide. iQUAM's --work-dir, --log-dir and --output-dir are placement detail the caller cannot know on DPS, so they keep in-container defaults.

Fan-in: the manifest mechanism

L2P's granules and MRVA's BIC + iQUAM inputs are variable-count, which a scalar flag cannot express. Each is instead a single --<name>-manifest flag pointing at a JSON file; see Input contract for the schema. localize_manifest fetches the manifest, then materializes every listed entry into a scratch directory using its relative_path.

A CWL Directory input, which MAAP would stage in automatically, was considered and rejected for three reasons:

  • There is no single prefix to stage. L2P's granules are arbitrary hrefs across PO.DAAC collections; MRVA's fan-in spans roughly thirty unrelated DPS output prefixes.
  • It would over-fetch catastrophically. A Directory on seasonal/ would transfer the whole ~141 GB archive to read the one 396 MB file that day needs.
  • It cannot carry identity. The manifest's sensor and relative_path fields reproduce the <SENSOR>/<YEAR>/<file> layout mrva4com_container.m's per-sensor scan expects. A staged directory arrives in whatever shape the producer happened to use.

Stage-out, and who chooses the path

CWL collects glob: ./output* relative to the job's working directory. Anything written to an absolute path outside it is simply not collected — a job would run to completion and stage out an empty directory.

All four containers therefore derive their output root from MUR_OUTPUT_ROOT, defaulting to $PWD/output. run_mur_pipeline.py passes MUR_OUTPUT_ROOT=/data/output so local behaviour is unchanged. MRVA is the exception: its paths are compiled into mrva4com_container.m, so until the next MATLAB rebuild the entrypoint symlinks /data/output/{csp,netcdf} at the real output directory, with a copy fallback if the symlink is refused. It logs which branch fired.

Who controls a path. Anything we write — static resources, manifests, promoted artifacts, STAC items — goes to a key we choose. Anything DPS writes lands under dps_output/<algorithm>/<tag>/<date>/<time>/, where the job tag is the only caller-controlled component. That split is what the promotion step below exists to bridge.

Where generated files are catalogued

Three layers, with different owners.

1. Jobs — MAAP maintains this

maap.list_jobs() is a queryable record of every job ever submitted, filterable by process, status, queue, tag and datetime range. Nothing to maintain. This is why job tags are deterministic and self-describing (mur.<run_id>.<role>.<key>) — it makes that catalogue queryable by meaning rather than by opaque id. But it is job-shaped, not product-shaped: finding a particular BIC means first finding the job that produced it.

2. Intermediates — deterministic keys, not STAC

BIC files, iQUAM .bii, landice per-day outputs and the .c06 coefficient are promoted after their job succeeds: copied from the DPS-chosen path to a canonical key under the workspace bucket (mur_maap/paths.py). That converts a path we do not control into one we do, at the one moment we still hold the job id.

Without it, the BIC cache is decorative — an artifact left where DPS put it is invisible to tomorrow's run, whose only route back to it is a job id a later invocation does not have. Promotion is what makes --prior-csp-file work too: this day's coefficient lands at a known key, and the next day's run chains from it instead of bootstrapping.

These are deliberately not registered in STAC. They churn daily, they are internal plumbing, and cataloguing them would mean thousands of items nobody queries. A single S3 HEAD is cheaper and simpler than a catalogue round-trip.

3. The products — MAAP's own STAC, written by the containers

The product is where discovery is the point, and MAAP has a documented mechanism for it that this project initially missed. An algorithm writes a catalog.json into its stage-out directory and MAAP ingests it automatically — no registration request, no approval, no public bucket:

ServiceWhat it is for
dps-stac.maap-project.orgthe API. /catalogs/user-<username> is yours — note the user- prefix, which the tutorial omits; the bare form 404s
dps-stac-browser.maap-project.orga human-facing browser
titiler-dps-stac.maap-project.orgtiles any catalogued raster

common/bin/write_stac.py emits that catalog. It is shipped in both the mrva and cog images, which describe the granules and the browse rasters respectively. It is stdlib-only because neither image has pip — python3 is present in both only as an awscli dependency — so the output is validated against the real pystac in tests/test_write_stac.py, before an image is built rather than inside one.

This is why products do not need promoting. Asset hrefs in the catalog are written relative to the Item file, and the ingest service rewrites them to absolute s3:// URLs. So a granule stays exactly where DPS put it and its STAC Item becomes its stable address. Copying a product to a canonical key duplicates roughly 730 MB per day to solve a problem MAAP had already solved.

The intermediates in section 2 are a different case: promotion there is a lookup index for the next day's submit, which would otherwise need a catalogue round-trip on the critical path.

Two naming rules that are not obvious

The collection id is assigned, not chosen, and cannot be constructed. Whatever id the catalog declares is discarded and replaced with <username>__<algorithm>__<version>, lowercased — where the algorithm name is the registered one, which MAAP suffixes with a number of its own:

jleach_jpl__mur-mrva_1756__2.0.14

That _1756 also appears in the registry CWL key and in the DPS output prefix. It is assigned at registration and exists nowhere in this repo, so it is read off a path a job already returned (stac.registered_algorithm(), recorded by _note_registered as the run goes) rather than guessed. The first version of this code built ids without it and printed links that all 404'd while looking perfectly plausible. utils/mur_stac.py asks the API instead, for the cases where no job href is in hand.

The version is part of the id too, so every algorithm version is its own collection — bumping mur-cog from 2.0.14 to 2.0.15 starts a new collection rather than adding to the old one.

The label is the title, not the id

The id is machine plumbing. What a browser listing shows is the title, and that is ours. Verified against a real ingested collection on 2026-10-09: title, description, extent and renders all survive ingest unchanged, and keywords, providers and item_assets survive on other users' collections. Only the id is rewritten. license is normalised (proprietary became other).

So the per-collection metadata lives in one table, COLLECTIONS in common/bin/write_stac.py — in the file rather than in entrypoint flags, because it is prose with commas, quotes and nested structure, and threading that through bash would be all quoting and no clarity. The entrypoints name a collection; the table says what that collection is.

The item id decides what overwrites what. Items sharing an id in a collection overwrite each other, regardless of job tag, which is what makes re-running a day idempotent. The two products use that differently on purpose:

ItemWritten byMode in the id?
mur-l4-20261006-nrtmrvayes — the interim and the final analysis are both real data, and must stay separately addressable
mur-cog-20261006-1kmcogno — a map should show one best picture per day, so a REA reprocess replaces the NRT browse layer

The browse rasters hold celsius, not GHRSST's packed integers

GHRSST packs every field as a scaled integer — analysed_sst is int16 with scale_factor 0.001 and add_offset 298.15 — and gdal_translate writes those raw integers through, carrying scale and offset across as metadata rather than applying them. The first generation of these COGs did exactly that, and the result was a file whose pixels, histogram, statistics and pixel-inspect tools all reported numbers like -26800. Every consumer then had to know to ask for unscaling, and the catalogue's render parameters — which were in kelvin — clamped the whole globe into two bright bands.

So the COG step now converts. The browse rasters hold Float32 degrees celsius, and the netCDF granule remains the archival product in its original packing for anyone who wants the source values. No unscale anywhere, and a number read out of one of these files is a temperature.

FieldConversionWhy
sstcelsiusscale/offset, then −273.15
anom, errphysicalscale/offset only — a temperature difference is the same number in kelvin and celsius, and shifting it would turn a +2 K warm event into −271 C
icephysicalalready a fraction
maskrawa bit field; converting flags to float is nonsense

The conversion maps the entire integer domain linearly with -scale, computed from the band's own scale and offset, rather than using gdal_translate -unscale. Two reasons: -unscale yields kelvin with no way to shift to celsius in the same pass, and its interaction with the fill value could not be verified in the development environment. Mapping the whole domain leaves nothing to interpret — the fill maps to a known output value and that value is declared as the nodata, so fill pixels land on it whether or not GDAL treats them specially.

Because that reasoning was not testable locally, verify_conversion checks the result instead: after each raster is written it reads the statistics back and warns if the values fall outside a physically sensible range for that field. A browse raster holding kelvin, or raw counts, or an unmasked fill value looks identical to a correct one at a glance — it simply draws wrong somewhere else, days later. This turns that into one message in one job log.

Float32 costs roughly twice the bytes of the packed integers; PREDICTOR=3 recovers most but not all of it, and outdir_max for the module moved from 4096 to 8192 MiB to suit. That is the price of a file anyone can read without a manual.

A data observation, not a render problem. analysis_error on the MUR25 product has exactly two distinct values — 0.80 K over 340,992 pixels and 0.81 K over 9,253. No colour scale makes that informative, and a flat layer is the field telling the truth. An L4 analysis error would normally vary with observation density, so this is worth understanding before anyone reads meaning into the layer.

Nothing in this catalogue can be deleted

Verified two ways. Its OpenAPI document registers exactly two verbs across 21 routes — GET everywhere, and POST on /search, which is a query rather than a write. And live requests agree: DELETE on an item and on a collection both answer 405, with no Transaction among the API's 29 conformance classes. (maap-eoapi can expose collection writes as an opt-in; this deployment does not.) Ingestion is automatic and one-way. An ingested collection stays until MAAP removes it, which is a request to support@maap-project.org rather than a command.

Two consequences worth planning around. First, every algorithm version leaves a collection behind permanently, so the version in the collection id is not just a label — it is a row in a list that only grows. Second, and more sharply: deleting a version's objects while its STAC items survive makes things worse, not better. It turns an old collection nobody opens into a collection whose every link is broken, and that state cannot be undone. utils/mur_cleanup.py refuses to do it for that reason unless explicitly overridden; the right order is to have the collection dropped first, then delete the objects.

Collection metadata, by contrast, is NOT frozen. MAAP's own documentation is explicit: “Later jobs can overwrite metadata on generated Catalog and Collection records. Do not rely on manual edits to those records surviving ingestion.” So a collection that comes out with the wrong title is repaired by running another job at that same version — no version bump, and nothing to clean up.

One case here is unexplained: the 2.0.18 analysis collection ingested with no title, keywords or providers, while 2.0.15 through 2.0.17 carried all three. The image was current — its items' asset descriptions match this repository's text exactly — so the catalog it staged out did contain them. Recorded rather than rationalised; the items are correct and the gap is cosmetic.

No item_assets on the collection

It is the natural place to document each asset key once, and it cannot be used here. MAAP's STAC API merges item_assets into every item on read, including the keys an item does not have, with no href. titiler then walks the item's assets and answers

{"detail": "'href'"}

on the first one it finds. That broke the 1 km product specifically: it produces sst and anom while the collection described five fields, so three empty definitions were merged into every 1 km item and each tile request returned 500. MUR25 tiled fine, because it produces all five and nothing was merged in empty. Verified against the live API.

The titles, descriptions and units live on each item's own assets, which is what a browser displays. A collection-level copy is a nicety; tiling the flagship product is not.

Viewer links live in links, never in assets

An item carries a preview link to a rendered PNG and an alternate link to an interactive map, both served on demand by MAAP's tiler. They are links and not assets on purpose: see the next section — titiler computes an item's zoom bounds across all of its assets, so adding a PNG and an HTML page as assets would break the very tiling they exist to make reachable.

The container cannot work the URLs out for itself. They need the published collection id, which is assigned at ingest and carries a suffix MAAP allocates. The orchestrator passes it in through --stac-collection, having learned the suffix from any DPS output path it has already seen — one suffix is allocated per deployment and shared by every module, so mur-mrva_1756 names mur-cog_1756 too. Without it the links are omitted rather than guessed.

A raster item must not hold a non-raster asset

Verified against the live service on 2026-10-08. For an Item holding both a GeoTIFF and a Zarr, tilejson.json fails with

'/vsis3/…/output.zarr' does not exist in the file system,
and is not recognized as a supported dataset name

for every value of assets=, including the GeoTIFF's own key: it computes zoom bounds across all of the item's assets and dies on the first one it cannot open. /info?assets=<key> honours the parameter correctly, so the Item is not malformed — only tiling is affected.

So the granules and the browse rasters are separate Items in separate collections rather than one Item with a netCDF data asset beside its COGs. That split looked like a constraint imposed by MAAP's one-collection-per-algorithm rule; it turns out to be the only shape that tiles at all.

What is not this catalogue

stac.maap-project.org and titiler-pgstac front the curated catalogue — a managed archive of 37 collections of NASA campaign data (ABoVE, AFRISAR, GEDI and the like), with 29 conformance classes, no Transaction and no self-service registration. Nothing this pipeline produces could ever appear there, which is why for a while it appeared nowhere. Getting a product in is a request to MAAP's data team, not a code change.

The DPS STAC needs no such request, and nothing has to be marked public: a collection there is readable anonymously the moment it is ingested — confirmed by fetching one over plain HTTP from a machine holding no MAAP, AWS or Earthdata credentials at all. The sidecar Item that MaapPyClient.publish_stac_item still writes into the workspace bucket is not the published Item. The dataviewer, utils/mur_stac.py and utils/mur_layers.py all read the DPS STAC; the dataviewer falls back to the sidecar only for a day MAAP has not ingested yet, since the sidecar is readable the instant a run finishes. The sidecar carries the granule and its MUR25 sibling but no browse rasters: those are catalogued by the cog jobs themselves, which is why the run does not wait for them.

The static resources are not catalogued either, for the same reason as the intermediates: containers receive explicit hrefs built by joining a configured root with a fixed relative path, so nothing ever searches for them.

Surviving an idle-culled workspace

One analysis day is 28 jobs — landice, iQUAM, 25 L2P jobs across five sensors and their day windows, then MRVA. That is far longer than any idle timeout, and the JupyterHub server is culled when idle. The home directory and the S3 buckets persist; a running process does not.

So the orchestrator persists submitted job ids and per-stage status, and is re-enterable rather than blocking. Two fields carry the design:

  • reference_today is frozen at run creation. Recomputing it on resume would shift the NRT/REA boundary and every rewrite decision mid-flight, days after the jobs were planned.
  • config_fingerprint refuses a resume against an edited config, which would silently change what already- submitted jobs mean.

If the state file itself is lost, every job tag is recomputable from the plan alone, so list_jobs(tag=…) rebuilds it from live MAAP truth.

Still unverified

Each of these is an assumption that has not met a real endpoint. They are listed rather than resolved because guessing would be worse than waiting.

  • get_job_result()'s return shape — a directory prefix, per-file hrefs, or a dict keyed by CWL output id. It gates output matching, so one real landice job should be run and its response recorded before any code is written against it.
  • A queue offering 64 GiB and 16 cores for MRVA. Nothing else needs one. Worth confirming before registering anything, since it is the cheapest question to ask and the most expensive to discover late.
  • DPS ephemeral disk. L2P materializes every granule to scratch — a MODIS day is roughly 288 granules at ~20 MB, and a worst case exceeds 20 GB. outdir_max does not reserve scratch.
  • Outbound egress from DPS workers. landice fetches OSI-SAF sea ice; iQUAM fetches NOAA STAR. (A worker does reach ghcr.io and S3, so egress is not blocked wholesale.)
  • The runtime UID/GID, which decides whether MRVA's symlink stage-out works or falls back to copying.
  • submit_job(inputs=)'s shape — plain {"name": value} or OGC {"name": {"value": …}}, and whether non-string scalars are accepted.
  • list_jobs(tag=) — exact or prefix matching, and whether dedup keys on inputs or tag. Promotion to canonical keys was chosen partly so cross-run lookup does not depend on the answer.

L2P granules are copied into the workspace bucket before a job reads them. A real job confirmed why: handed PO.DAAC's own href, the container fails with An error occurred (403) when calling the HeadObject operation: Forbidden on podaac-ops-cumulus-protected. A worker reads S3 as its own role, and that role has no DAAC access.

The same job proved the other half — it downloaded its manifest from the workspace bucket seconds earlier, so a worker reads that perfectly well. Copying costs duplicate storage and is the price of the 403. The cleaner fix is teaching localize.sh to mint Earthdata credentials, but it touches the file all four containers share and means rebuilding every image; a maap.granule_staging switch keeps the direct path available for when that changes.
