Deploying to MAAP

From a MAAP account to a processed day: staging ~142 GiB of static data, publishing the images, registering four algorithms, and launching the first job.

On this page
  • 0. Ask MAAP ops first
  • 1. Start an OGC workspace
  • 2. Get a token that works off-platform
  • 3. Stage the static data
  • 4. Build and publish the images
  • 5. Generate, validate, deploy
  • 6. One landice job, by hand
  • 7. A full day

This is the procedure. For how any of it works — the CWL model, the manifest fan-in, promotion, the catalogue split — see Running on MAAP.

The order is a dependency chain, not a preference. Step 3's fast path gates the smoke test in step 6, and step 6 gates writing any client code.

0. Ask MAAP ops first

Does any DPS queue offer 64 GiB and 16 cores? MRVA is the only module that needs a large instance — landice, iQUAM and L2P all fit on small ones. If no queue reaches it, that is a blocking finding for the whole migration, and it costs one email now versus discovering it after three algorithms are already registered.

Three more worth putting in the same message:

  • Ephemeral disk on the worker. L2P materializes every granule to scratch before MATLAB runs — a MODIS day is roughly 288 granules at ~20 MB, and a worst case exceeds 20 GB. outdir_max does not reserve scratch.
  • Outbound internet from workers. landice fetches OSI-SAF sea ice; iQUAM fetches NOAA STAR.
  • Queue names available to you.

1. Start an OGC workspace

The image choice gates OGC entirely. The default ADE and standard Hub images ship the non-OGC v4 stack; only custom images carry maap-py ≥ 5, Algorithm Registration ≥ v1 and Jobs ≥ v2. The published workspace table has blank image-path cells, so the container registry is the only authoritative source.

At hub.maap-project.org, log in with NASA Earthdata, choose Other from the Environment dropdown, and paste:

mas.maap-project.org/root/maap-workspaces/2i2c/pangeo:v6.0.0

Then once, in the workspace terminal. The home directory persists across sessions and across workspaces, so this survives restarts:

git clone <mur repo> ~/mur
cd ~/mur && pip install -e . --no-deps
pip install 'boto3>=1.34' earthaccess

python -c "import mur_maap, maap; print('ok')"

--no-deps is deliberate: the image already pins numpy, netCDF4 and matplotlib, and the orchestrator needs only stdlib plus boto3, maap-py and earthaccess.

2. Get a token that works off-platform

Inside a workspace, authentication is ambient — MAAP() just works. Anywhere else, maap-py needs MAAP_PGT. It is not an AWS profile: maap-py exchanges that token for temporary AWS credentials itself.

# in the workspace, confirm what the environment already has
printf %s "$MAAP_PGT" | wc -c
printf %s "$MAAP_PGT" | sha256sum

If that is empty, generate one at console.maap-project.org/profile/tokens, which exists for off-platform automation.

A MAAP token is jwt: followed by a JWT, and a JWT always begins eyJ (base64 for {"). Selecting a wrapped value with the mouse in a browser terminal can clip a leading character, leaving wt:eyJ…. The value still looks like a long opaque blob, the length is one short, and the server answers only {"message": "Invalid session or insufficient permissions."}. Compare length and hash at both ends rather than eyeballing it; --check also flags a clipped prefix.

On the target host, keep it out of shell history:

read -rsp 'MAAP_PGT: ' MAAP_PGT && export MAAP_PGT

# or persist it, which is worth it if a long upload needs restarting
umask 077
printf 'export MAAP_PGT=%q\n' 'PASTE_HERE' > ~/.maap-token
source ~/.maap-token

3. Stage the static data

377 objects, ~142 GiB. Run the environment check first — it proves the things that otherwise fail late:

python utils/upload_static_resources.py --check

It reports whether MAAP_PGT is set and well-formed, whether maap-py is ≥ 5, which bucket and prefix your credentials grant, when they expire, and — the one a HEAD cannot tell you — whether a real write succeeds, by doing a put/get/delete round-trip on a probe key. It finishes by printing the config values it discovered.

GetBucketLocation returning AccessDenied is expected and harmless. The workspace session policy scopes you to your own prefix rather than bucket metadata; uploads are unaffected.

Pick the right source mode

The static tree exists in two shapes, and choosing wrongly produces a plan full of missing files rather than an error that explains itself.

FlagUse when
--from-config <config>The tree is assembled under one root — the usual case. Reads landice.static_resources_dir, so the upload reads exactly the tree the local pipeline reads.
--source-root <dir>Same shape, path given explicitly.
--from-prod-layoutThe files are still scattered across their original NAS locations (GRIDS_DIR, ICE_DIR, SEASONAL_DIR, POLARCAP_FILE).

Run it where the data is

Uploading from the host that holds the data moves the bytes once and needs no scratch disk. Going via an intermediate machine moves twice that and needs 142 GiB free. Do not tar first — that produces a single 142 GiB archive which then has to be unpacked somewhere to become objects again.

# look before moving anything: prints every resolved source path,
# and flags whatever is missing
python utils/upload_static_resources.py \
    --from-config config.container.json --include-optional \
    --dest s3://maap-ops-workspace/<user>/mur/static-resources --dry-run

# then, under nohup so a dropped connection does not kill it
nohup python utils/upload_static_resources.py \
    --from-config config.container.json --include-optional \
    --dest s3://maap-ops-workspace/<user>/mur/static-resources \
    --ledger ~/mur_static_ledger.jsonl > ~/mur_upload.log 2>&1 &

If that host cannot install maap-py or reach the MAAP API, credentials can come from elsewhere. --credentials-command is re-run on every refresh, so anything that mints fresh credentials works — including an ssh back to a workspace. Copying a credential set across by hand cannot work: they expire in about an hour and the upload takes several.

Resuming

Re-run the identical command. A ledger records each completed file and is fsync'd per line, so a killed run loses at most the file in flight; anything not in the ledger is checked with a HEAD. There is no risk of a truncated object — S3 only materializes one when the multipart upload completes, so a resume finds either a whole file or nothing.

A killed run does leave the parts it had already uploaded. They are invisible to a normal listing and billed as storage:

python utils/upload_static_resources.py ... --abort-stale-multiparts

Verify from the workspace

python utils/upload_static_resources.py --verify-only --include-optional

Three layers, of which the second is the one that matters: it calls the orchestrator's own resolve_landice_static_hrefs() and resolve_mrva_static_hrefs() against the real bucket for all 366 days, including the 366 → 365 fold. If that passes, the orchestrator cannot fail on a missing static input, because the question was answered by the same code that will ask it.

4. Build and publish the images

Two builds. The base images carry the MATLAB Runtime and need a Linux x86-64 host with licence access. The -dps variants are metadata only and take about a second each.

# an explicit tag, not the default branch-and-hash: the CWL pins
# dockerPull to an exact tag and algorithm_version must match it
./utils/build_and_push.sh --push --tag 1.0.0

./utils/build_dps_images.sh --tag 1.0.0 --push --verify

A CWL DockerRequirement carries no registry credentials, so DPS cannot pull a private package. --verify checks anonymous pull; if it fails, make each package public in the registry's settings.

5. Generate, validate, deploy

pip install cwltool ogc_ap_validator pyyaml
./utils/generate_cwl.sh

That generates each workflow from maap/<module>/algorithm_config.yml, cross-checks that dockerPull is your image rather than a placeholder and that NetworkAccess is present, then runs cwltool --validate --strict and ap-validator. The generated CWL is committed, because it is the deployment artifact and the generator expects hand-edits.

Deploy from the workspace, cheapest first:

from maap.maap import MAAP
maap = MAAP()

for m in ['iquam', 'landice', 'l2p', 'mrva']:
    r = maap.deploy_algorithm_from_cwl_file(
        file_path=f'/home/jovyan/mur/maap/cwl_workflows/process_mur-{m}_1.0.0.cwl')
    print(m, r.status_code, r.json())      # 202 == accepted

maap.get_deployment_status(deployment_id).json()["status"]
maap.list_algorithms().json()

That order is not arbitrary. Each step proves exactly one new mechanism: iQUAM has no static inputs and no S3 reads, so it proves registration and stage-out; landice proves S3 static localization; L2P proves the manifest fan-in and the scratch-disk assumption; MRVA proves the large queue.

6. One landice job, by hand

Stop here before writing client code. get_job_result()'s return shape is undocumented — it may be a directory prefix, per-file hrefs, or a dict keyed by CWL output id — and three later pieces depend on which. Run one job, record the response verbatim, then build against what it actually returns.

root = "s3://maap-ops-workspace/<user>/mur/static-resources"

resp = maap.submit_job(
    process_id="mur-landice:1.0.0",
    queue="<queue from MAAP ops>",
    tag="mur.smoke.landice",            # also organises dps_output/
    inputs={
        "year": "2026", "doy": "164",
        "landmask-p01-file":         f"{root}/grids/maskGLOBp01deg.gds",
        "gridindex-north-p01-file":  f"{root}/mat/p01/saf2north.mat",
        "gridindex-south-p01-file":  f"{root}/mat/p01/saf2south.mat",
        "landmask-p011-file":        f"{root}/grids/maskGlob1km.gds",
        "gridindex-north-p011-file": f"{root}/mat/p011/saf2north.mat",
        "gridindex-south-p011-file": f"{root}/mat/p011/saf2south.mat",
    })
job_id = resp.json()["id"]

maap.get_job_status(job_id).json()

import json; print(json.dumps(maap.get_job_result(job_id).json(), indent=2))

Three things to confirm from that output: that output/ contains p01/ and p011/ with real files — if it is empty, stage-out is wrong and nothing downstream can work; the real names behind landice_ice_p011, landice_grid_p01 and landice_icefiles_p011; and which subdirectory icefiles_YYYY_DDD.txt lands in.

Stage-out can be rehearsed locally first, without touching MAAP. Note the -w and the absence of any -v …:/output — that deliberately emulates CWL's “working directory is the output directory” contract:

mkdir -p /tmp/cwl-smoke
docker run --rm --platform linux/amd64 --user "$(id -u):$(id -g)" --group-add 0 \
  -v /tmp/cwl-smoke:/tmp/cwl-smoke -w /tmp/cwl-smoke \
  ghcr.io/podaac/mur/landice-dps:1.0.0 --year 2026 --doy 164 --landmask-p01-file ...

ls -R /tmp/cwl-smoke/output      # empty here means empty on DPS

7. A full day

One analysis day is 28 jobs: landice, iQUAM, 25 L2P jobs across five sensors and their day windows, then MRVA. Far longer than any idle timeout, which is why the run is checkpointed rather than blocking.

# offline, no credentials needed: exercises every decision, path builder
# and argument dict, and prints the full job table
mur-maap run --config config.maap.json -p -1 --dry-run

# --once does one non-blocking sweep and exits; exit code 2 means
# "still running", so watch or cron drives it trivially
mur-maap run --config config.maap.json -p -1 --preprocess-only --once
mur-maap status --latest
mur-maap resume --latest --once        # after each cull

The mur-maap CLI is designed but not yet implemented — see Current state. Until it exists, MAAPOrchestrator can be driven directly from a notebook once MAAPClient is real.

Outputs accumulate under ~/my-private-bucket/dps_output/<algorithm>/<tag>/…, which is a real path in the workspace filesystem — so the existing viewer reads them with no changes:

mur-viewer ~/my-private-bucket/dps_output/mur-mrva/<tag>/.../*.nc --info
mur-web-viewer                          # Streamlit on :8501
